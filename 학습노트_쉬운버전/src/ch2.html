1처리량과 응답 시간

사용자는 성능을 "결과가 늦게 뜬다", "타임아웃이 난다"로 체감해요. 성능 지표는 여러 가지지만, 서버를 볼 때 가장 중요한 두 가지는 응답 시간과 처리량이에요.

  • 요청 전송: 서버에 연결(TCP)하고, 약속된 형식(예: HTTP POST + JSON)으로 데이터를 보내는 시간
  • 서버 처리: 서버가 로직을 실행하고 DB·외부 API를 호출해 응답을 만드는 시간
  • 응답 전송: 만들어진 응답이 네트워크를 타고 돌아오는 시간

측정 기준: TTFB와 TTLB

지표의미식당 비유
TTFB
Time To First Byte		응답의 첫 바이트가 도착할 때까지첫 접시가 나올 때까지
TTLB
Time To Last Byte		응답의 마지막 바이트가 도착할 때까지코스 요리가 전부 나올 때까지

응답이 작으면 둘의 차이가 거의 없어요. 하지만 파일 다운로드처럼 데이터가 크거나 네트워크가 느리면 차이가 커져요. 응답 시간은 보통 1초가 안 되기 때문에 밀리초(ms, 1/1000초)로 적어요. (0.025초 = 25ms)

직접 해보기 · 터미널에서 TTFB / TTLB 재기
curl -o /dev/null -s \
  -w "TTFB: %{time_starttransfer}s\nTTLB: %{time_total}s\n" \
  https://example.com/api/articles

# 출력 예
# TTFB: 0.182s   ← 첫 바이트 도착
# TTLB: 0.195s   ← 전부 도착 (작은 JSON이라 차이가 거의 없음)

브라우저 개발자 도구(F12) → Network 탭 → 요청 클릭 → Timing 에서도 같은 값을 볼 수 있어요.

왜 응답 시간이 중요할까
  • 구글 실험(2009, "Speed Matters"): 검색 지연이 100ms 늘면 사용자당 검색 수 0.2% 감소, 400ms 늘면 0.6% 감소. 지연을 되돌린 뒤에도 감소세가 한동안 이어졌어요.
  • 아마존: 응답 시간이 100ms 늘 때마다 매출이 약 1% 줄어든다는 통계.
  • 결론: 빠르다고 매출이 꼭 느는 건 아니지만, 느려지면 손해라는 것은 분명해요.

서버 처리 시간은 어디에 쓰일까

서버 처리 시간은 ① 로직 수행(if, for) ② DB 연동(SQL) ③ 외부 API 연동 ④ 응답 데이터 생성으로 이루어져요. 이 중 DB 연동과 외부 API 연동이 압도적이에요. 저자가 실제로 잰 한 요청(전체 348ms)은 이랬어요.

외부 API가 없는 서비스라면 보통 DB 연동이 70~80% 이상을 차지해요. 그래서 응답 시간을 줄일 때는 DB와 API 연동 시간부터 봐요.

신입이 자주 하는 착각

"for 문을 stream으로 바꾸면 빨라지겠지?" — 로직은 전체의 5% 수준이에요. 5%를 절반으로 줄여도 2.5% 개선이지만, SQL 한 번을 줄이면 수십 ms가 줄어요. 코드 한 줄보다 "DB·API를 몇 번 부르는가"를 먼저 세어 보세요.

직접 해보기 · 어디서 시간이 걸리는지 로그로 남기기
public OrderDetail getOrderDetail(long orderId) {
    long t0 = System.currentTimeMillis();

    Order order = orderDao.findById(orderId);           // DB 조회
    long t1 = System.currentTimeMillis();

    Delivery delivery = deliveryApi.getStatus(orderId); // 외부 API 호출
    long t2 = System.currentTimeMillis();

    OrderDetail result = OrderDetail.of(order, delivery); // 순수 로직
    long t3 = System.currentTimeMillis();

    log.info("orderDetail db={}ms api={}ms logic={}ms total={}ms",
            t1 - t0, t2 - t1, t3 - t2, t3 - t0);
    return result;
}
// 로그 예: orderDetail db=38ms api=190ms logic=1ms total=229ms
//          → 고칠 곳은 로직이 아니라 외부 API 구간!

1-2처리량 (throughput)

단위 시간(보통 1초) 동안 시스템이 처리한 요청 수.
용어 풀이 · TPS와 RPS

TPS(Transactions Per Second, 초당 트랜잭션 수), RPS(Requests Per Second, 초당 요청 수). 엄밀히는 다르지만 실무에서는 섞어 써요. 이 노트는 책처럼 TPS로 통일해요.

계산은 단순해요. 1분 동안 600건을 처리했다면 600 ÷ 60 = 10 TPS.

① 동시 처리 수 늘리기

한 번에 처리할 수 있는 요청 수를 늘려 대기 자체를 없애요. (서버 증설, 풀 크기 조정 등)

② 처리 시간 줄이기

요청 하나를 빨리 끝내 같은 시간에 더 많이 처리해요. (쿼리 개선, 캐시, 압축 등)

→ 이 장의 나머지 내용은 전부 이 두 방법 중 하나에 속해요.

먼저 측정하라

트래픽이 많은 시간대의 TPS와 응답 시간을 측정하고 → 목표치를 정하고 → 개선안을 찾는 순서로 가요. 가장 쉬운 방법은 스카우터, 핀포인트, 뉴렐릭 같은 모니터링 도구(APM)로 실시간·과거 TPS를 보는 거예요.

직접 해보기 · 도구가 없을 때, 접근 로그로 초당 요청 수 세기

2서버 성능 개선 기초 — 병목 지점과 확장

2-1병목 지점

전체 속도는 가장 느린 한 곳(병목)이 결정한다. 그곳을 찾는 게 먼저.
비유로 이해하기

병(bottle)의 목(neck)이 좁으면 병이 아무리 커도 물은 천천히 나와요. 4차선 도로가 한 구간만 1차선이면 전체가 막히는 것과 같아요. 병목이 아닌 곳을 넓혀 봐야 소용없어요.

서비스 초기에는 사용자·데이터가 적어 문제가 드물어요. 규모가 커지면 가끔 느려지기 시작하고, 방치하면 큰 장애가 돼요. 전형적인 증상은 이래요.

  • 순간적으로 모든 요청이 심하게 느려짐 — 10초 이상 걸리고 연결 시간 초과 오류가 쏟아짐
  • 서버를 재시작하면 잠깐 괜찮다가 다시 느려지는 일이 반복
  • 트래픽이 줄어들 때까지 상황이 계속됨

핵심 원인은 시스템의 최대 TPS를 넘는 트래픽이에요. TPS를 높이려면 먼저 문제 지점을 찾아야 해요.

  1. 오래 걸리는 작업을 찾는다 — 감이 아니라 실제 실행 시간 측정으로
  2. 모니터링 도구의 실행 시간 추적 기능으로 어떤 코드·쿼리가 느린지 확인한다
  3. 도구가 없으면 의심 가는 코드의 실행 시간을 로그로라도 남긴다 (1-1의 예제처럼) → 재발했을 때 원인 파악이 쉬워져요

2-2수직 확장 (scale-up)

장비 한 대의 사양(CPU·메모리·디스크)을 올리는 가장 빠른 응급처치.

원인을 찾았으면 우선 급한 불부터 끄고 근본 해결책을 찾아요. 수직 확장은 더 빠른 CPU, 코어 추가, 메모리 증설, HDD→SSD 교체처럼 자원을 키우는 방법이고, 클라우드에서는 특히 빨리 적용할 수 있어요.

사용자가 조금만 몰려도 전체가 멈추던 서비스. 원인은 쿼리·테이블 설계였지만 고치려면 시간이 필요했어요. 우선 DB 장비의 CPU와 메모리를 올려 서비스를 다시 열었어요. 완전히 멈추는 것보다 다소 느려도 제공하는 편이 낫고, 근본 해결책을 마련할 시간도 벌 수 있었어요.

서버에도 통해요. 메모리 512MB로 동시 200개를 처리하던 서버에 동시 요청이 250개로 늘면 느려지기 시작하는데, 메모리를 1GB로 늘리기만 해도 TPS가 올라요.

한계: 트래픽이 계속 늘면 다시 문제가 생겨요. 매번 수직 확장할 수는 없어요. ① 비용이 크고 ② 장비 한 대의 용량에도 상한이 있기 때문이에요.

3DB 커넥션 풀

DB 연결은 만드는 데 오래 걸리니, 미리 만들어 두고 빌려 쓰고 돌려준다.

그리고 서버를 수평 확장하는 것도 결국 풀 크기를 늘리는 것이에요. (서버 3대 × 풀 20 = DB 연결 60개 → 4대면 80개) 서버를 늘리기 전에 DB 상태부터 확인하세요.

3-2커넥션 대기 시간

빈 커넥션이 없을 때 "얼마나 기다릴지". 짧게 잡아서 빨리 실패시키는 편이 낫다.

이 시간 안에 커넥션을 못 얻으면 DB 연결 실패 에러가 나요. 기다린 만큼 응답 시간도 늘어나는데, HikariCP 기본값은 30초라서 최악의 경우 응답이 30초를 넘겨요.

  • 응답 시간이 중요한 서비스는 0.5초~3초로 짧게
  • 짧게 잡으면 풀이 꽉 찼을 때 "잠시 후 다시 시도해 주세요" 같은 응답을 빨리 줄 수 있어요. 한참 무응답인 것보다 빨리 에러를 주는 편이 낫고, 서버 부하가 불어나는 것도 막아요.

예시: 풀 10, 동시 요청 30개, DB 부하로 쿼리가 10초로 늘어난 상황

대기 시간 30초 (기본값 그대로)

5초 시점: 10개는 쿼리 실행 중, 20개는 대기 중. 기다리다 지친 10명이 새로 고침(재요청).

서버는 취소된 요청을 바로 멈추지 않으므로 대기가 30개로 늘고, 처리해야 할 요청이 40개가 돼요. 재요청이 반복될수록 부하가 눈덩이처럼 불어나요.

대기 시간 1초

2초 시점: 10개는 쿼리 실행 중, 커넥션을 못 얻은 20개는 이미 오류 응답을 받고 끝남.

동시 처리 수가 10개로 유지되어 서버 부하가 일정 수준에서 안정돼요.

알아두기 · 이 에러 메시지를 보면 "풀이 꽉 찼구나"
java.sql.SQLTransientConnectionException: HikariPool-1 -
  Connection is not available, request timed out after 3000ms.

커넥션을 기다리다 대기 시간(여기선 3초)을 넘겼다는 뜻이에요. 원인은 대개 ① 느린 쿼리가 커넥션을 오래 잡고 있거나 ② 풀 크기가 트래픽에 비해 작거나 ③ 커넥션을 반납하지 않는 코드(close 누락)예요.

4서버 캐시

자주 조회하는 데이터를 (키, 값)으로 가까이에 저장해 두고, DB 대신 거기서 꺼내 쓴다.

DB를 확장하면 비용이 크고, 수평 확장해도 쿼리 실행 시간 자체는 크게 줄지 않아요. DB를 늘리지 않고 응답 시간과 처리량을 개선하고 싶을 때 캐시를 써요.

비유로 이해하기

자주 쓰는 전화번호는 수첩을 뒤지지 않고 포스트잇에 적어 모니터에 붙여 두죠. 캐시가 바로 그 포스트잇이에요. 다만 번호가 바뀌면 포스트잇도 고쳐 써야 하고(무효화), 붙일 자리도 한정돼 있어요(삭제 규칙).

private final Map<Long, Article> cache = new ConcurrentHashMap<>();

public Article getArticle(long id) {
    Article cached = cache.get(id);          // 1) 캐시에서 먼저 찾는다
    if (cached != null) {
        return cached;                       // 2) 있으면(hit) DB에 안 가고 바로 반환
    }
    Article article = articleDao.findById(id); // 3) 없으면(miss) DB에서 조회
    cache.put(id, article);                  // 4) 다음을 위해 캐시에 저장
    return article;
}

DB 조회 결과뿐 아니라 복잡한 계산 결과나 외부 API 응답도 캐시에 담을 수 있어요.

① 데이터가 끝없이 쌓여 메모리가 터져요(최대 개수 없음). ② 글이 수정돼도 옛 내용이 영원히 나와요(만료·무효화 없음). 아래 4-1 ~ 4-4가 바로 이 두 문제를 푸는 내용이에요.

알아두기 · 캐시 키 정하기

4-1적중률과 삭제 규칙

적중률(hit rate) = 캐시에 있던 횟수 ÷ 캐시 조회 시도 횟수   (100번 조회 중 87번 있었다면 87%)

적중률이 높을수록 DB에 덜 가므로 응답 시간 ↓ · 처리량 ↑ · DB 부하 ↓.

가장 단순한 방법은 많이 넣는 거예요(상품 5,000개 중 4,500개를 넣으면 100개만 넣을 때보다 훨씬 잘 맞겠죠). 하지만 캐시는 메모리를 쓰니 한계가 있어요(예: 최대 1,000개). 꽉 찬 상태에서 새 데이터를 넣으려면 하나를 빼야 하는데, 누구를 뺄지 정하는 게 삭제 규칙이에요.

규칙빼는 대상책상 정리로 치면
LRU Least Recently Used가장 오래전에 사용된 것제일 오랫동안 안 꺼내 본 서류부터 치움
LFU Least Frequently Used가장 적게 사용된 것꺼내 본 횟수가 제일 적은 서류부터 치움
FIFO First In First Out가장 먼저 들어온 것책상에 올려 둔 지 가장 오래된 서류부터 치움
예제로 이해하기 · 크기 3짜리 LRU 캐시

A, B, C가 들어 있어요. A를 조회한 다음 D를 넣으면 누가 빠질까요? → 가장 오래 안 쓰인 B가 빠져요. (A는 방금 썼으니 살아남음)

// LinkedHashMap의 세 번째 인자 true = "최근에 쓴 순서"로 정렬
Map<String, String> lru = new LinkedHashMap<>(16, 0.75f, true) {
    @Override
    protected boolean removeEldestEntry(Map.Entry<String, String> eldest) {
        return size() > 3;          // 3개를 넘으면 가장 오래 안 쓴 것 제거
    }
};
lru.put("A", "1"); lru.put("B", "2"); lru.put("C", "3");
lru.get("A");                       // A를 방금 사용함
lru.put("D", "4");                  // 꽉 찼으니 하나 제거됨
System.out.println(lru.keySet());   // [C, A, D]  ← B가 빠졌다
용어 풀이 · 유효 시간 (TTL, Time To Live)

많은 서비스는 최신 데이터(최신 기사·영상)를 더 자주 봐요. 오래된 데이터는 캐시에 있어도 안 쓰일 가능성이 크니, 꽉 차지 않았더라도 일정 시간이 지나면 자동 삭제되게 해요. 이 시간이 TTL(만료 시간)이에요.

private final Cache<Long, Article> cache = Caffeine.newBuilder()
        .maximumSize(1_000)                        // 최대 1,000개 (넘으면 자동 삭제)
        .expireAfterWrite(Duration.ofMinutes(10))  // 저장 후 10분 지나면 만료 (TTL)
        .build();

public Article getArticle(long id) {
    // 있으면 꺼내고, 없으면 뒤의 함수로 DB에서 읽어 저장까지 해 준다
    return cache.get(id, key -> articleDao.findById(key));
}

  • 규모가 큰 데이터 → 리모트: 대형 쇼핑몰의 개별 상품 정보. 로컬은 메모리가 부족해요.
  • 배포가 잦은 서비스 → 리모트 적극 고려: 로컬은 재시작할 때마다 캐시를 처음부터 다시 쌓아야 해서 배포 직후가 느려져요.
public String getProductJson(long productId) {
    String key = "products:" + productId;

    String cached = redis.opsForValue().get(key);     // 1) 캐시 서버에서 조회
    if (cached != null) return cached;                // 2) hit → 바로 반환

    String json = toJson(productDao.findById(productId)); // 3) miss → DB 조회
    redis.opsForValue().set(key, json, Duration.ofMinutes(10)); // 4) TTL 10분으로 저장
    return json;
}

4-3캐시 사전 적재

사람이 몰릴 게 뻔하면, 몰리기 "전에" 캐시를 미리 채워 둔다.
가상 사례 · G 앱의 월 요금 안내

사용자 300만 명. 매달 정해진 날 전체 회원에게 요금 안내 푸시를 보내요. 절반이 바로 확인하면 단시간에 150만 명이 몰려요.

문제: 각자의 요금 정보는 아직 한 번도 조회된 적이 없어서 캐시에 없어요 → 적중률이 0%에 가깝고, 응답 지연과 DB 부하가 폭증해요.

해결: 푸시를 보내기 전에 각 사용자의 요금 정보를 캐시에 넣어 둬요 → 적중률 99% 가까이 유지, DB 부하 집중 방지.

// 푸시 발송 배치의 앞 단계에서 실행
for (Member m : memberDao.findAllForBilling()) {

        "bills:" + m.getId(), toJson(bill), Duration.ofDays(3));
}
// 캐시가 다 채워진 뒤에 푸시를 보낸다

4-4캐시 무효화

원본이 바뀌면 캐시도 바꾸거나 지운다. 안 그러면 사용자가 옛 정보를 본다.

무효화 시점은 데이터 성격에 따라 달라요.

  • 민감한 데이터(가격, 게시글 내용): 변경 즉시 무효화. 글을 고쳤는데 옛 글이 보이면 사용자는 혼란스럽고, 오류 신고를 하거나 서비스를 불신해요.
  • 민감하지 않고 작은 데이터: TTL로 주기적으로 갱신해도 충분해요. 예) 인기 글 목록 TTL 10분 → 10분마다 새로 고쳐짐. 더 자주 원하면 1분.
@Transactional
public void changePrice(long productId, int newPrice) {
    productDao.updatePrice(productId, newPrice);   // 1) 원본(DB) 변경
    redis.delete("products:" + productId);         // 2) 캐시 삭제
    // 다음 조회 때 miss → DB의 새 가격을 읽어 캐시에 다시 저장된다
}
흔한 실수 · 가격처럼 민감한 데이터를 로컬 캐시에 두기

로컬 캐시는 자기 서버 것만 지워져요. 서버 A에서 가격을 바꾸면 A의 캐시는 갱신되지만 서버 B의 캐시에는 옛 가격이 남아 있어요. 그래서 로드 밸런서가 A로 보낸 사용자는 새 가격을, B로 보낸 사용자는 옛 가격을 봐요. 변경에 민감한 데이터는 모든 서버가 함께 보는 리모트 캐시에 두세요.

5가비지 컬렉터와 메모리 사용

메모리를 한꺼번에 많이 쓰면 GC가 오래 걸리고, 심하면 서버가 죽는다. "조금씩 나눠서" 다루자.

자바, Go, 파이썬 등은 가비지 컬렉터(GC)를 써요. 다 쓴 객체를 그 즉시 지우지 않고, 정해진 규칙(힙 사용량이 일정 비율 초과, 일정 주기 등)에 따라 안 쓰는 메모리를 찾아 한꺼번에 정리해요.

비유로 이해하기

손님이 나갈 때마다 치우지 않고, 빈 그릇이 어느 정도 쌓이면 영업을 잠깐 멈추고 한꺼번에 치우는 식당이에요. 편하긴 한데 치우는 동안은 주문을 못 받아요. 테이블이 넓고 그릇이 많을수록 치우는 시간도 길어져요.

  • 장점: 개발자가 메모리를 직접 관리하지 않아도 됨. 메모리를 직접 다루지 않아 보안 문제도 줄어듦
  • 단점: 응답 시간에 영향. 자바는 GC 동안 애플리케이션이 일시 정지해요 → 이걸 Stop-The-World라고 해요

메모리를 많이 쓰고 객체가 많을수록 GC 시간이 길어져요. 반대로 JVM 최대 힙을 4GB → 2GB로 줄이면 검사 대상이 줄어 GC가 짧아질 수 있어요. 단, 실제로 4GB 가까이 필요한 앱이면 메모리 부족 에러가 나니 실제 사용 패턴에 맞춰 조정해요.

# JVM 최대 힙 크기는 실행 옵션으로 정한다
java -Xmx2g -jar app.jar      # 최대 힙 2GB

5-1대량 객체 생성 주의

게시글 1개 ≈ 0.5KB × 10만 개 ≈ 50MB → 동시에 100명이 호출하면 약 4.9GB 필요

최대 메모리가 4GB라면 메모리 부족이에요. GC를 아무리 돌려도 필요한 양 자체가 4.9GB라서 해결되지 않아요. 답은 "한 번에 가져오는 양을 제한"하는 것.

  • 조회 범위 제한: 10년 치 거래 내역 대신 최대 3개월 치만
  • 조회 개수 제한: 한 번에 가져올 수 있는 개수를 트래픽과 메모리에 맞춰 제한

✗ 조건 없이 전부

-- 10년 치가 전부 메모리에 올라온다
select *
from trade
where userId = 100;

✓ 기간 + 개수 제한

select id, amount, tradeDt
from trade
where userId = 100
  and tradeDt >= '2026-08-17' -- 최근 3개월
order by tradeDt desc
limit 100;                    -- 최대 100건

5-2스트림 활용

파일 다운로드처럼 큰 데이터는 전체를 메모리에 올리지 말고, 조금씩 읽어서 바로 보내요(스트림).

비유로 이해하기

수영장 물을 옮길 때 거대한 통에 한 번에 담아 나르면 통이 수영장만큼 커야 해요. 호스로 흘려보내면 호스 굵기만큼의 공간이면 충분하죠. 스트림이 호스예요.

// ✗ 파일 전체를 메모리에 올림 → 30MB 파일을 100명이 받으면 약 3GB 필요
byte[] all = Files.readAllBytes(path);
out.write(all);
// ✓ 8KB 버퍼로 나눠 읽고 쓰기 → 100명이 받아도 약 800KB
try (InputStream in = Files.newInputStream(path)) {
    byte[] buf = new byte[8 * 1024];
    int n;
    while ((n = in.read(buf)) != -1) {   // 8KB씩 읽어서
        out.write(buf, 0, n);            // 읽은 만큼 바로 내보낸다
    }
}
// Java 9+ 에서는 in.transferTo(out) 한 줄로 같은 동작

전체 로딩(약 3GB)과 비교하면 스트림 방식(약 800KB)의 메모리 사용량은 0.03% 수준 — 수천 분의 일이에요.

실제 사례 · 엑셀 다운로드 한 번에 서버가 멈춤

내부 관리 사이트 서버 2대 중 1대가 응답하지 않았어요. JVM 메모리를 다 쓰고, 풀 GC가 여러 번 돌아도 포화 상태가 이어지다 결국 OOME(Out Of Memory Error) 발생.

메모리 상태(힙 덤프)를 분석하니 엑셀 생성 객체가 대부분을 차지. 누군가 수백만 건 엑셀 다운로드를 눌렀고, 오래 걸리자 취소하고 다시 눌러서 같은 데이터가 또 메모리에 올라갔던 거예요.

조치: ① 엑셀을 메모리가 아니라 파일에 스트림으로 생성 ② DB 조회 결과도 리스트로 한 번에 받지 않고 스트림으로 순차 처리 → 이후 재발 없음.

읽을거리 · 디스코드가 러스트로 간 이유

디스코드는 Go로 만든 서버를 러스트로 다시 만들었어요. 이유는 GC로 인한 응답 시간 증가와 CPU 사용률 급등. GC가 없는 러스트로 개선했어요.

그렇다고 무조건 러스트로 갈 일은 아니에요. 대규모 트래픽·고성능이 필수가 아니라면 GC 영향은 대체로 크지 않고, GC 성능도 계속 좋아지고 있어요. 다른 개선책을 먼저 검토하고, 그래도 안 될 때 고려해요.

6응답 데이터 압축

보내는 데이터를 줄이면 전송 시간도, 트래픽 비용도 줄어든다. 설정 몇 줄이면 된다.

응답 시간에는 데이터 전송 시간이 포함되고, 전송 시간은 ① 네트워크 속도 ② 전송 데이터 크기에 달려 있어요. 사용자의 네트워크 속도는 서버가 못 바꾸지만 데이터 크기는 줄일 수 있어요.

  • HTML, CSS, JS, JSON 같은 텍스트는 압축 효과가 커요 — gzip으로 70% 이상 줄기도 해요
  • 클라우드는 트래픽이 곧 비용이라 압축은 비용 절감에도 직결돼요
  • 아파치, Nginx 같은 웹 서버에 기능이 있어 설정만 추가하면 바로 효과를 봐요
용어 풀이 · 브라우저와 서버가 압축을 "협상"하는 방법
[요청]  Accept-Encoding: gzip, deflate      ← 브라우저: "나 gzip, deflate 풀 수 있어"
[응답]  Content-Encoding: gzip              ← 서버: "그럼 gzip으로 압축해서 보낼게"

클라이언트가 처리할 수 있는 압축 방식을 Accept-Encoding 요청 헤더로 알리면, 서버는 그중 하나로 압축하고 Content-Encoding 응답 헤더로 무엇을 썼는지 알려 줘요.

Nginx에서 켜기

gzip on;
# html은 기본 포함, 나머지 텍스트 추가
gzip_types text/css
           application/javascript
           application/json;
gzip_min_length 1024;  # 1KB 이상만

Spring Boot에서 켜기

server:
  compression:
    enabled: true
    mime-types: text/html,text/css,application/javascript,application/json
    min-response-size: 1024
직접 해보기 · 정말 압축되고 있는지 확인
curl -s -o /dev/null -D - -H "Accept-Encoding: gzip" https://example.com/api/articles

# 응답 헤더에 아래 줄이 보이면 압축 성공
# Content-Encoding: gzip
압축할 때 주의할 점
  • 텍스트만 압축해요. JPEG 이미지, zip 파일처럼 이미 압축된 데이터는 다시 압축해도 효과가 없고 CPU만 써요.
  • 웹 서버에서 압축했는데도 응답이 압축되지 않았다면, 중간의 방화벽이 압축을 풀어서 보내고 있지 않은지 확인해요.
알아두기 · 응답 크기는 곧 돈

AWS 같은 클라우드는 트래픽 양에 비례해 과금해요. 규모가 커질수록 데이터 크기만 줄여도 절감액이 커져요. IDC(온프레미스)도 네트워크 대역폭에 따라 비용이 달라져요. 트래픽이 늘고 있다면 응답 크기를 줄일 수 있는지 확인해 보세요.

7정적 자원과 브라우저 캐시 / CDN

7-1동적 자원 vs 정적 자원

구분특징예
동적 자원요청할 때마다 결과가 달라질 수 있음상품 목록 HTML, 상품 상세 JSON
정적 자원같은 URL이면 항상 같은 데이터이미지, JS, CSS

정적 자원은 트래픽에서 큰 비중을 차지해요. 한 쇼핑몰 첫 페이지를 측정했더니 전체 4.0MB 중 이렇게 나왔어요.

이미지 3.0MB (약 75%)
JS 775KB (19%)
기타
그림 11. 이미지와 JS가 약 94%(약 3.7MB) — HTML·JSON·CSS는 다 합쳐도 6% 남짓

브라우저 개발자 도구(F12) → Network 탭에서 종류별 용량을 쉽게 확인할 수 있어요.

7-2브라우저 캐시

"이 파일은 60초 동안 다시 물어보지 마" 하고 브라우저에게 알려 준다.

같은 페이지에 들어갈 때마다 같은 이미지·JS를 다시 받으면, 서버엔 불필요한 트래픽과 비용이, 사용자에겐 느린 화면이 생겨요. (상품 상세를 10번 보면 같은 파일을 10번 다운로드)

해결책은 클라이언트(브라우저) 캐시. HTTP 응답의 Cache-Control(또는 Expires) 헤더로 브라우저가 응답을 일정 시간 보관하게 해요.

Cache-Control: max-age=60     ← 60초 동안은 서버에 다시 요청하지 말고 저장해 둔 것을 써라

브라우저는 파일을 로컬(메모리·디스크)에 보관하고, 60초 안에 같은 주소가 필요하면 서버에 가지 않고 그것을 써요 → 화면이 빨라지고 서버 전송 비용도 줄어요.

Nginx — 정적 파일에 7일 캐시

location ~* \.(js|css|png|jpg)$ {
    expires 7d;
    # → Cache-Control: max-age=604800
}

Spring — 응답에 직접 지정

return ResponseEntity.ok()
    .cacheControl(CacheControl
        .maxAge(60, TimeUnit.SECONDS))
    .body(notices);
한 걸음 더 · 캐시 기간이 긴데 파일을 고치면? (책 범위 밖 보충)

캐시를 7일로 줬는데 app.js를 수정하면 사용자는 최대 7일간 옛 파일을 봐요. 그래서 실무에서는 파일 이름에 버전을 넣어요: app.3f9a1c.js, app.js?v=20261117. 내용이 바뀌면 URL이 바뀌니 브라우저가 새 파일로 인식해요.

7-3CDN (Content Delivery Network)

정적 파일을 우리 서버 대신, 사용자와 가까운 곳의 전용 서버들이 나눠서 전달해 준다.

브라우저 캐시는 브라우저마다 따로 동작해요. 그래서 많은 사용자가 동시에 처음 접속하면 여전히 대량의 이미지·JS·CSS를 보내야 하고, 네트워크가 금방 포화돼요. (4차선 도로에 차 몇 대는 잘 지나가지만 수십 대가 몰리면 순식간에 막히는 것과 같아요.)

해결책 중 하나가 콘텐츠 전송 전용 네트워크 CDN이에요. 대표 서비스: Amazon CloudFront, Akamai, Cloudflare.

그림 12. 사용자는 가까운 에지 서버에서 받고, 에지에 없을 때만 오리진에서 가져온다
비유로 이해하기

본사 창고(오리진) 한 곳에서 전국에 택배를 보내면 멀수록 느리고 창고도 붐벼요. 지역마다 물류 거점(에지)을 두고 인기 상품을 미리 갖다 두면, 고객은 가까운 거점에서 받고 본사 창고는 한가해져요.

  • 사용자는 CDN이 제공하는 URL로 접근해요. 예) https://cdn.example.com/images/shoes.jpg
  • 에지에 파일이 없으면 오리진에서 가져와 전달하고 캐시에 보관 → 이후 같은 요청은 에지가 바로 응답. 같은 파일을 수만 번 요청해도 오리진은 한 번만 처리하면 돼요.
  • 장점 3가지: ① 오리진 트래픽 감소 ② 콘텐츠를 빠르게 제공 ③ 트래픽 비용 절감 → 서비스가 성장하기 시작하면 도입을 고려해요.
흔한 실수 · 정적 파일 크기를 관리하지 않기

실수로 30MB짜리 이미지를 올려 비용 청구가 급증한 사례가 있어요. 계약상 트래픽 한도가 있으면 용량 초과로 서비스가 멈출 수도 있어요. 업로드 파일 크기를 관리하고, 웹 서버에 크기 제한을 걸어 두세요.

client_max_body_size 5m;   # 5MB 넘는 업로드는 413 에러로 거절 (Nginx)

8대기 처리

순간 폭증에 맞춰 장비를 키우는 대신, 감당할 만큼만 받고 나머지는 줄을 세운다.

콘서트 예매처럼 짧은 시간에 폭증했다가 매진과 함께 급감하는 트래픽이 있어요. 대응 방법은 두 가지예요.

방법 1. 미리 증설한다 → 비용 문제

  • 서버는 클라우드에서 쉽게 늘리고 줄일 수 있어요.
  • 하지만 DB는 쉽게 늘릴 수 없고, 한 번 올리면 다시 줄이기도 어려워요.
  • 30일 중 폭증 1시간은 약 0.14%. 그 순간을 위해 비싼 DB 고정비를 올리는 건 부담이에요.

방법 2. 받을 만큼만 받고 대기시킨다

  • 감당 가능한 수준까지만 들여보내고 나머지는 줄을 세워요 — 사용자 대기 시스템.
  • 은행 창구와 같아요. 창구가 다 차면 번호표를 뽑고 기다리고, 창구가 비면 다음 번호가 들어가요.

그림 13. 대기 처리 — 동시 입장 수를 제한하고 나머지는 순서대로 대기

이점

  • 서버를 증설하지 않고도 서비스를 안정적으로 제공해요.
  • 새로 고침하면 순번이 뒤로 밀리니 사용자가 새로 고침을 자제해요 → 새로 고침 폭증도 막아요.

사용자는 기다리기 싫어하지만, 과부하로 아예 안 되는 것보다는 기다렸다가 결국 쓸 수 있는 편이 나아요.

private final Semaphore gate = new Semaphore(100);    // 입장권 100장

public ReserveResult reserve(ReserveRequest req) {
    if (!gate.tryAcquire()) {                         // 입장권이 없으면
        return ReserveResult.waiting("접속자가 많아요. 잠시만 기다려 주세요.");
    }
    try {
        return doReserve(req);                        // 입장한 사람만 실제 예매 처리
    } finally {
        gate.release();                               // 끝나면 입장권 반납
    }
}

※ 위 코드는 서버 1대 안에서만 동작하는 원리 설명용이에요. 실제 대기 시스템은 서버 여러 대가 함께 보는 저장소(예: Redis)에 순번을 기록해 "몇 번째인지"를 알려 줘요.

알아두기

대규모 트래픽 아키텍처를 직접 만들어 보고 싶은 마음이 들어도, 개발자는 비용을 함께 생각해야 해요. 그런 점에서 대기 제어는 매우 합리적이에요. 직접 구현하지 않아도 이미 여러 솔루션이 있어 빠르게 도입할 수 있다는 것도 장점이에요.

내 프로젝트에서 확인해 볼 것

  • 우리 서비스의 평소 TPS와 평균 응답 시간을 숫자로 말할 수 있다 (모니터링 도구 또는 접근 로그)
  • 가장 느린 API 3개가 무엇이고, 그 안에서 DB·외부 API가 몇 ms를 쓰는지 안다
  • 커넥션 풀의 최대 크기와 대기 시간(connection-timeout)이 얼마로 설정돼 있는지 확인했다
  • 서버 대수 × 풀 크기가 DB의 최대 연결 수를 넘지 않는다
  • 캐시를 쓴다면 최대 크기와 TTL이 있고, 데이터 변경 시 무효화 코드가 있다
  • "전체 조회" API에 기간·개수 제한(limit)이 걸려 있다
  • 대용량 파일·엑셀 다운로드가 스트림 방식이다
  • JSON 응답에 Content-Encoding: gzip이 붙어 있다
  • 이미지·JS·CSS 응답에 Cache-Control 헤더가 붙어 있고, 업로드 크기 제한이 있다
