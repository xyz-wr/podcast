1성능에 핵심인 DB

DB가 느려지면 연결된 모든 서버가 느려진다. 그리고 대부분은 DB 탓이 아니라 "쓰는 방법" 탓이다.
실제 사례 · H 서비스의 출석 체크 대란

교사·학생 대상 서비스. 코로나로 재택 수업이 시작되며 가입자가 급증했고, 출석 체크 시간(8시 40분)이 다가오면 응답이 10초를 넘기며 에러가 쏟아졌어요.

원인: 사용자가 조금만 늘어도 DB CPU가 90%를 넘었어요. 자주 호출되는 기능에 풀 스캔을 일으키는 쿼리가 있었고, 데이터가 쌓일수록 쿼리가 느려지는데 트래픽까지 늘어 응답 시간이 계속 늘어난 거예요.

용어 풀이 · 풀 스캔(full scan)

테이블의 모든 데이터를 순서대로 읽는 것. 주로 where 조건에 맞는 인덱스가 없을 때 발생하고, 인덱스보다 전체를 읽는 편이 빠르다고 DB가 판단해도 발생해요.

무서운 점은 데이터가 적을 땐 티가 안 난다는 거예요. 개발할 때 100건으로는 빠르던 쿼리가, 운영에서 1,000만 건이 되면 어느 순간 급격히 느려져요. 그래서 설계할 때 항상 풀 스캔 가능성을 염두에 둬요.

2조회 트래픽을 고려한 인덱스 설계

인덱스는 "어떤 조건으로, 얼마나 자주, 얼마나 많은 데이터를 조회하는가"를 보고 정한다.

대부분의 시스템은 조회 비율이 높아요(게시판: 다수는 읽기만 하고 일부만 씀). 그리고 같은 게시판이라도 규모에 따라 답이 달라요. 아래 테이블과 쿼리로 생각해 봐요.

article 테이블

create table article (
  id       int primary key,
  category int,
  writerId int,
  title    varchar(255),
  content  text,
  regdt    timestamp
);

카테고리별 목록 조회

select id, category, writerId,
       title, content
from article
where category = 10
order by id desc
limit 20, 10;

limit 20, 10 = 20개를 건너뛰고 10개 (3페이지)

category에 인덱스가 없다면? 서비스 규모에 따라 결과가 완전히 달라요.

사내 공지 게시판인기 커뮤니티
데이터량주 1건 → 1년 52건, 10년 해도 520건하루 5,000건 × 약 6년 ≈ 1,000만 건
트래픽직원 1,000명이 5분 안에 다 읽어도 약 3.34 TPS다수 사용자가 동시에 목록 조회
결론풀 스캔해도 문제없음 → 인덱스 불필요매번 1,000만 건 비교 + 풀 스캔이 겹쳐 DB CPU 100% → 인덱스 필수
create index idx_article_category on article (category);   -- 카테고리별 목록용
create index idx_article_writer   on article (writerId);   -- '내가 쓴 글' 목록용

show index from article;     -- 이 테이블에 어떤 인덱스가 있는지 확인

원칙: 조회 패턴을 기준으로 인덱스를 설계해요. '내가 쓴 글 목록' 기능이 있다면 where writerId = ?로 조회할 테니 writerId를 포함한 인덱스가 필요해요.

알아두기 · 중간 포함 검색(like '%검색어%')은 인덱스를 못 쓴다

찾아보기는 앞 글자 순서로 정렬돼 있어요. "김"으로 시작하는 이름은 바로 찾지만, 이름 중간에 "민"이 들어간 사람은 처음부터 다 훑어야 하죠.

select * from article where title like '%검색어%';  -- ✗ 풀 스캔
select * from member  where name  like '지은%';     -- ✓ 앞부분 일치는 인덱스 사용 가능

제목·본문 검색이 필요하면 ① 엘라스틱서치 같은 검색 엔진을 쓰거나 ② DB의 전문(full-text) 검색 기능(Oracle Text, MySQL FULLTEXT 인덱스)을 써요.

2-1단일 인덱스와 복합 인덱스

예제 테이블: 사용자 활동 로그. 일평균 방문 10만 명 × 평균 5회 활동 → 하루 50만 건, 한 달 1,500만 건. 대규모는 아니지만 알맞은 인덱스가 없으면 문제가 생기는 규모예요.

create table activityLog (
  id               int primary key,
  userId           int,
  activityType     varchar(20),    -- VISIT, BUY ...
  activityDate     date,
  activityDatetime timestamp,
  memo             varchar(200)
);
비유로 이해하기 · 복합 인덱스 = 전화번호부

전화번호부는 (성, 이름) 순으로 정렬돼 있어요. "김"씨를 찾기도 쉽고, "김 + 지은"을 찾기는 더 쉬워요. 하지만 성을 모르고 이름 "지은"만으로는 못 찾아요 — 처음부터 다 봐야 해요.

복합 인덱스 (userId, activityDate)도 같아요. 앞 칼럼(userId)부터 조건에 있어야 인덱스를 제대로 써요.

인덱스 (userId, activityDate)가 있을 때인덱스 활용
where userId = 123✓
where userId = 123 and activityDate = '2024-07-31'✓ (가장 효과적)
where activityDate = '2024-07-31' (앞 칼럼 userId가 없음)✗

예 1) 고객센터: 특정 사용자의 일자별 활동 조회

select * from activityLog
where userId = 123 and activityDate = '2024-07-31'
order by activityDatetime desc;

userId를 포함한 인덱스는 필수. 고민은 activityDate까지 넣을지예요 → 단일 (userId) vs 복합 (userId, activityDate). 사용자 한 명당 데이터가 얼마나 쌓이는지로 판단해요.

사용 패턴사용자당 데이터판단
주 1회 방문 · 5건1년 260건, 5년 약 1,300건수천 건 이하 비교는 0.1초 이내 → 단일 인덱스로 충분
매일 방문 · 30건 이상1년 1만 건 이상, 사용자당 수만 건userId로 좁혀도 너무 많음 → 복합 인덱스 필요
create index idx_log_user      on activityLog (userId);                 -- 단일
create index idx_log_user_date on activityLog (userId, activityDate);   -- 복합

예 2) 통계: 특정 일자의 활동 타입별 개수

select activityDate, activityType, count(activityType)
from activityLog
where activityDate = '2024-07-28'
group by activityType;
  • 풀 스캔을 피하려면 activityDate 인덱스가 필요해요. activityType까지 넣을지는 실행 빈도와 실행 시간으로 정해요.
  • activityDate만 인덱스면 그날 50만 건을 모두 읽어 10초 이상 걸릴 수 있어요. 하지만 하루 한 번 실행해 결과를 별도 테이블에 저장한다면 30초 걸려도 괜찮아요.
  • 하루 데이터가 수백만 건으로 커지면 (activityDate, activityType) 복합 인덱스를 적용해요 → 인덱스 값만으로 결과를 구할 수 있어요(커버링 인덱스, 2-3).

2-2선택도를 고려한 인덱스 칼럼 선택

값이 다양한 칼럼(선택도가 높은 칼럼)일수록 인덱스로 많이 걸러낼 수 있다.
용어 풀이 · 선택도(selectivity)

인덱스 칼럼의 고유한 값 비율. 회원 100만 명 테이블에서 memberId는 100만 가지(선택도 최고), gender는 3가지(선택도 최저)예요.

-- 선택도 직접 계산해 보기 (1에 가까울수록 높음)
select count(distinct gender) / count(*) from member;   -- 예: 0.000003
select * from member where gender = 'F' and birthyear = 1990;

gender 값이 M 50만, F 50만, N 1천 개라면, gender 인덱스를 타도 여전히 50만 건을 확인해야 해요. 반으로밖에 못 줄이니 효율이 낮아요.

비유로 이해하기

도서관에서 "한국어로 쓰인 책"으로 찾으면 거의 전부가 해당돼서 도움이 안 돼요. "ISBN"으로 찾으면 딱 한 권이 나오죠. 찾아보기는 많이 걸러 줄수록 가치가 있어요.

예외 · 선택도가 낮아도 인덱스가 맞는 경우 — 작업 큐
create table jobqueue (
  jobid  varchar(16) not null primary key,
  status char(1) not null    -- W(대기) / P(처리 중) / C(완료)
);
select * from jobqueue where status = 'W' order by jobid asc;

고유 값이 3개뿐이라 선택도는 낮아요. 하지만 대부분은 C(완료)이고 W·P는 극소수이며, 작업 실행기는 W만 계속 조회해요. 인덱스가 없으면 매번 풀 스캔이라 모든 작업이 지연돼요.

→ 선택도 숫자만 볼 게 아니라 "내가 찾는 값이 전체에서 얼마나 적은가"를 봐야 해요. 100만 건 중 W가 50건이라면 status 인덱스는 아주 효과적이에요.

2-3커버링 인덱스 활용하기

쿼리에 필요한 칼럼이 인덱스에 전부 들어 있으면, 실제 테이블을 읽지 않아도 돼서 빠르다.
비유로 이해하기

책의 찾아보기에 "트랜잭션 … 212쪽"이라고 적혀 있어요. 궁금한 게 "몇 쪽에 나오는지"뿐이라면 찾아보기만 보고 끝이에요. 본문을 펼칠 필요가 없죠. 필요한 답이 찾아보기에 이미 다 있는 것 — 이게 커버링 인덱스예요.

인덱스 (activityDate, activityType)이 있다고 할 때 두 쿼리를 비교해 봐요.

✗ select * — 테이블까지 읽음

select *
from activityLog
where activityDate = '2024-07-31'
  and activityType = 'VISIT';

인덱스로 대상은 빨리 찾지만, memo 같은 칼럼 값을 얻으려면 각 행의 실제 데이터를 읽어 와야 해요.

✓ 인덱스에 있는 칼럼만 조회

select activityDate, activityType
from activityLog
where activityDate = '2024-07-31'
  and activityType = 'VISIT';

필요한 칼럼이 모두 인덱스에 있어 실제 데이터에 접근하지 않아요. explain의 Extra에 Using index가 떠요.

실무 팁 · select * 습관 줄이기

필요한 칼럼만 적으면 ① 커버링 인덱스를 탈 기회가 생기고 ② 네트워크로 오가는 데이터가 줄고 ③ 서버 메모리도 덜 써요. 특히 text 같은 큰 칼럼이 있는 테이블에서 차이가 커요.

2-4인덱스는 필요한 만큼만 만들기

인덱스는 조회를 빠르게 하지만 쓰기를 느리게 하고 공간을 먹는다. 효과가 적으면 손해.

자주 쓰는 쿼리가 다음 두 개라고 해 봐요.

select * from activityLog
where userId = 123 and activityDate = '2024-07-31'
order by activityDatetime desc;

select * from activityLog
where userId = 123 and activityDate = '2024-07-31' and activityType = 'BUY'
order by activityDatetime desc;

둘 다 빠르게 하려고 (userId, activityDate)와 (userId, activityDate, activityType) 두 개를 만들 수도 있어요. 하지만 두 번째 인덱스가 효과를 보려면 한 사용자가 하루에 만드는 데이터가 아주 많아야 해요. 하루 수백 건 미만이면 첫 번째 인덱스만으로 이미 충분히 좁혀져서 차이를 느끼기 어려워요.

효과가 적은 인덱스는 오히려 손해
  • 데이터를 추가·변경·삭제할 때마다 인덱스도 함께 고쳐야 해서 쓰기가 느려져요. (인덱스 5개면 insert 한 번에 5곳을 더 고침)
  • 인덱스도 데이터라서 많아질수록 메모리·디스크를 더 써요.

요구사항을 살짝 바꿔 기존 인덱스 활용하기

새 쿼리가 기존 인덱스를 못 쓴다면, 인덱스를 추가하기 전에 요구사항을 조금 바꿀 수 있는지 먼저 검토해요.

create table reservation (
  id          bigint not null primary key,
  name        varchar(30) not null,
  reserveDate date not null,
  state       char(2) not null,
  regDt       timestamp not null
);
create index idxRdate on reservation (reserveDate);   -- 인덱스는 예약일에만 있음

✗ "예약자 이름으로 조회"

select * from reservation
where name = '홍길동'
order by regDt desc;

name 인덱스가 없어 풀 스캔.

✓ "특정 일자 + 예약자 이름으로 조회"

select * from reservation
where reserveDate = '2024-08-09'
  and name = '홍길동';

idxRdate로 그 날짜 데이터만 읽고 이름을 비교. 새 인덱스 없이 풀 스캔을 피해요.

→ 기획자에게 "예약 조회 화면에 날짜 선택을 필수로 넣으면 어떨까요?"라고 제안하는 것도 성능 개선이에요.

읽을거리 · 같은 칼럼에 인덱스를 또 만들지 않기

오래된 테이블은 기능이 붙을 때마다 인덱스가 늘고 담당자도 바뀌어요. 왜 있는지 모르는 인덱스가 생기고, 그러다 같은 칼럼 인덱스를 중복으로 만들기도 해요. 같은 칼럼 인덱스가 2개라고 조회가 두 배 빨라지지 않아요. 관리 비용만 늘어요.

새 인덱스를 만들기 전에 show index from 테이블명;으로 같은 효과를 낼 인덱스가 이미 있는지 먼저 확인하세요.

3-1미리 집계하기

조회할 때마다 count 하지 말고, 데이터가 추가될 때 숫자 칼럼을 +1 해 둔다.

설문 조사 기능이 있어요. 설문 목록 화면에 답변 수와 '좋아요' 수를 보여 줘야 해요.

테이블칼럼
survey (설문)surveyId (PK), subject, 기간, question1~4
answer (답변)surveyId + memberId (PK), answer1~4
liked (좋아요)surveyId + memberId (PK)

가장 먼저 떠오르는 방법은 목록을 조회하면서 서브 쿼리로 세는 거예요.

select s.surveyId, s.subject,
  (select count(*) from answer a where a.surveyId = s.surveyId) as answerCnt,
  (select count(*) from liked  l where l.surveyId = s.surveyId) as likedCnt
from survey s
order by s.surveyId desc
limit 30;

논리적으로는 맞지만 성능이 문제예요. 설문 30개, 설문당 평균 답변 10만 건, 좋아요 1만 건이라면:

  • 목록 조회 1번 (0.01초)
  • 답변 수 세는 서브 쿼리 30번 — 각각 10만 건을 셈 (0.1초씩)
  • 좋아요 수 세는 서브 쿼리 30번 — 각각 1만 건을 셈 (0.05초씩)
총 61번 실행 · 0.01 + (0.1 × 30) + (0.05 × 30) = 4.51초
비유로 이해하기

누가 "오늘 손님 몇 명 왔어요?"라고 물을 때마다 영수증 더미를 처음부터 세는 가게와, 손님이 올 때마다 카운터의 계수기를 한 번 누르는 가게. 후자는 물어보면 숫자만 읽어 주면 돼요.

해결: survey 테이블에 answerCnt, likedCnt 칼럼을 추가하고, 답변·좋아요가 생길 때마다 값을 바꿔요.

alter table survey
  add column answerCnt int not null default 0,
  add column likedCnt  int not null default 0;
-- 답변 등록: 답변 추가 + 카운트 증가
insert into answer values (1, 100, '답1', '답2', '답3', '답4');
update survey set answerCnt = answerCnt + 1 where surveyId = 1;

-- 좋아요 취소: 좋아요 삭제 + 카운트 감소
delete from liked where surveyId = 1 and memberId = 100;
update survey set likedCnt = likedCnt - 1 where surveyId = 1;
select surveyId, subject, answerCnt, likedCnt
from survey
order by surveyId desc
limit 30;
@Transactional
public void submitAnswer(long surveyId, long memberId, Answers answers) {

Q. 이렇게 중복 저장(비정규화)해도 괜찮나요?

정규화는 중복을 줄이고 데이터가 어긋나지 않게 구조화하는 것이에요. answerCnt는 answer 테이블에서 구할 수 있는 값을 중복 저장한 것이라, 실제 개수와 어긋날 수도 있어요.

그래도 이 경우엔 괜찮다고 봐요. 실제 10,150개인데 10,149로 보여도 목록을 보는 사람에게는 심각하지 않아요. 정확한 값이 필요한 최종 보고서는 관리 도구에서 answer·liked 테이블을 직접 세면 돼요.

Q. 동시에 여러 명이 답변하면 숫자가 꼬이지 않나요? (동시성)

증감은 반드시 쿼리 한 줄로 하세요. 값을 읽어 와서 코드에서 +1 하면 꼬여요.

// ✗ 읽고 → 더하고 → 쓰기: 두 요청이 동시에 10을 읽으면 둘 다 11을 써서 1이 사라진다
int cnt = surveyDao.selectAnswerCnt(surveyId);     // A: 10 읽음, B: 10 읽음
surveyDao.updateAnswerCnt(surveyId, cnt + 1);      // A: 11 저장, B: 11 저장 (12여야 함!)

// ✓ DB가 한 번에 처리하도록 쿼리 안에서 증가
// update survey set answerCnt = answerCnt + 1 where surveyId = ?

다만 "쿼리 한 줄이면 항상 안전"한지는 DBMS와 트랜잭션 격리 수준에 따라 달라요. 증감 쿼리를 쓸 때는 사용 중인 DBMS에서 원자적(atomic)으로 처리되는지 확인해야 해요.

3-2페이지 기준 대신 ID 기준 목록 조회

offset은 건너뛸 개수만큼 "세는" 시간이 든다. 마지막으로 본 ID 다음부터 읽으면 셀 필요가 없다.

게시글 10만 개를 10개씩 보여 주면 1만 페이지. 첫 페이지는 10개만 읽지만 마지막 페이지는 이래요.

select id, subject, writer, regdt from article
order by id desc
limit 10 offset 99990;     -- 99,990개를 건너뛰고 10개

DB는 어떤 id가 99,991번째인지 모르기 때문에 99,990개를 하나씩 센 뒤 10개를 읽어요. 뒤 페이지로 갈수록 느려지는 이유예요.

offset 방식 (limit 10 offset 99990)
99,990개를 세면서 건너뜀 (버려지는 일)
10개
ID 기준 방식 (where id < 마지막ID limit 10)
인덱스로 시작 위치에 바로 이동 → 세지 않음
10개
그림 3. offset은 앞부분을 세느라 시간을 쓰고, ID 기준은 필요한 10개만 읽는다
비유로 이해하기

책에서 "300번째 문단"을 찾으려면 처음부터 문단을 세어야 해요. 하지만 책갈피를 꽂아 뒀다면 바로 펼쳐서 이어 읽을 수 있죠. "마지막으로 본 ID"가 책갈피예요.

where 조건에 인덱스에 없는 칼럼이 있으면 더 느려요. 예) where deleted = false … limit 10 offset 10000 → deleted 값을 확인하려고 각 행을 실제로 읽어야 하고, 삭제된 행이 섞여 있어서 10,000개를 세려면 10,000개보다 더 읽어야 해요. deleted를 인덱스에 넣어도 세는 시간은 그대로 남아요.

해결: 마지막 ID를 기준으로 조회

-- 첫 10개 (결과의 마지막 id가 9985였다고 하자)
select * from article
where deleted = false
order by id desc limit 10;

-- 다음 10개: "9985보다 작은 것부터"
select * from article
where id < 9985 and deleted = false
order by id desc limit 10;

id는 PK(인덱스)라서 9985보다 작은 위치를 바로 찾아요. 스크롤을 내리면 다음 데이터를 불러오는 모바일 "더 보기" 화면과 특히 잘 맞아요(페이지 번호 대신 마지막 ID를 서버로 보냄).

실무 팁 · "다음 데이터가 더 있는지" 알려 주기 — 1개 더 조회

10개를 보여 줄 때 11개를 조회해요. 11개가 오면 "다음 있음"(앞 10개만 응답), 10개 이하면 "다음 없음".

public ArticlePage getArticles(Long lastId, int size) {
    // 첫 화면이면 lastId가 없으므로 가장 큰 값에서 시작
    long cursor = (lastId == null) ? Long.MAX_VALUE : lastId;

    // size + 1개를 조회: 한 개 더 읽어서 다음 페이지 유무를 판단
    List<Article> rows = jdbcTemplate.query(
        "select id, subject, writer, regdt from article " +
        "where id < ? and deleted = false order by id desc limit ?",
        articleMapper, cursor, size + 1);

    boolean hasNext = rows.size() > size;
    List<Article> items = hasNext ? rows.subList(0, size) : rows;
    return new ArticlePage(items, hasNext);
}
// 호출 예: GET /articles?size=10            → 첫 10개
//          GET /articles?lastId=9985&size=10 → 그다음 10개

3-3조회 범위를 시간 기준으로 제한하기

"전체에서 찾기"를 "하루치·한 달치·최근 것에서 찾기"로 바꾸면 읽을 데이터가 확 줄어든다.

포털 뉴스처럼 일자별로 목록을 제공하면 조회 범위가 하루로 제한돼요.

select title, regdt from news
where regdt >= '2024-08-09 00:00:00' and regdt < '2024-08-10 00:00:00'
order by regdt desc limit 100;
  • regdt 인덱스만 있으면 돼요. 하루 기사 수가 많지 않으면 and category = '01' 같은 조건을 더해도 인덱스 추가 없이 성능이 유지돼요.
  • 쇼핑몰 주문 내역도 "30개씩 끝없이" 대신 월별 조회로 하면, 인덱스 (customerId, orderDt)로 쿼리가 단순하고 빨라요.
select id, orderDt, totalPrice from orders
where customerId = 100
  and orderDt >= '2024-08-01 00:00:00' and orderDt < '2024-09-01 00:00:00'
order by orderDt desc;
실무 팁 · 날짜 범위는 "이상(>=) ~ 미만(<)"으로

between '2024-08-09 00:00:00' and '2024-08-09 23:59:59'처럼 쓰면 23:59:59.5 같은 데이터가 빠질 수 있어요. 위 예제처럼 시작일 이상, 다음 날 미만으로 쓰면 빈틈이 없어요.

최신 데이터만 조회하기

대부분의 기능은 최신 데이터를 주로 봐요. 매달 나오는 점검 결과도 고객은 최근 것에만 관심이 있으니 최근 6개월만 제공해도 돼요.

select * from checkResult
where cust_id = 100 and checkMonth >= '2024-03'    -- 6개월 전부터
order by checkMonth desc;

공지사항도 3년 전 것은 거의 안 읽어요. 최신 데이터만 보여 줘도 된다면 제품 담당자와 협의해 기능을 줄이고 구현을 단순하게 해요. (구글의 '최근 보안 활동'도 최근 28일만 보여 줘요.)

덤으로 얻는 효과 · DB 메모리 캐시 효율

DB는 조회한 데이터를 메모리에 캐시해 둬요. 범위를 최신으로 제한하면 자주 조회되는 데이터가 메모리에 올라 있을 확률이 높아져서 응답이 더 빨라져요.

3-4전체 개수 세지 않기

select id, name from member where name like '지은%' order by id desc limit 20;  -- 목록
select count(*) from member where name like '지은%';                            -- 전체 개수

목록 화면에서 "총 12,345건"을 보여 주려고 count 쿼리를 함께 실행하는 경우가 많아요. 그런데 목록 쿼리는 20개만 읽고 끝나지만, count는 조건에 맞는 데이터를 전부 세어야 해요. 데이터가 늘수록 count 시간도 늘어요(커버링 인덱스여도 인덱스를 끝까지 스캔해야 하고, 아니면 실제 데이터를 전부 읽어요).

조회가 느려지는 원인이 count 쿼리라면 실행하지 않는 방법을 고려해요. 서비스 담당자와 "전체 개수를 표시하지 않고 '더 보기'만 제공"하는 방향으로 협의해요. (3-2의 "1개 더 조회"와 잘 어울려요.)

읽을거리 · 평소 패턴을 알아야 이상 징후가 보인다

저자는 APM(성능 모니터링 도구)을 늘 띄워 둬요. 평소 응답 시간은 약 0.5초였는데, 어느 날 그래프의 띠가 살짝 위(약 0.7초)로 올라갔어요. 당장 문제 될 속도는 아니어서 넘길 수도 있었던 변화예요.

원인은 한 쿼리가 0.2초 느려진 것 — 서브 쿼리의 count가 데이터 증가로 느려진 거였어요. 미리 집계 방식(3-1)으로 바꾸자 0.4초로 줄었어요. 평소 숫자를 알고 있어야 작은 변화를 일찍 잡을 수 있어요.

3-5오래된 데이터 삭제 및 분리 보관

데이터 개수를 일정하게 유지하면 쿼리 시간도 일정하게 유지된다.

데이터가 늘면 쿼리 시간도 늘어요. 거꾸로, 개수를 일정하게 유지하면 실행 시간도 일정해요.

  • 예) 로그인 시도 내역: 낯선 지역 로그인 알림 같은 이상 징후 탐지용이라 최근 몇 달 치면 충분해요. 180일이 필요하다면 매일 181일 이전 데이터를 삭제해요.
  • 내부 관리용으로 과거 데이터가 필요하면, 서비스 DB에는 180일만 두고 그 이전은 별도 저장소로 분리 보관해요.
-- 181일 이전 로그인 내역 삭제 (한 번에 다 지우지 않고 1,000건씩 끊어서 반복)
delete from loginHistory
where loginDt < now() - interval 180 day
limit 1000;

※ 수백만 건을 한 번에 지우면 그동안 테이블에 부담을 줘요. 조금씩 끊어서 여러 번 지우는 게 안전해요.

알아두기 · 지웠는데 디스크 용량이 안 줄어요 — 단편화와 최적화

delete를 해도 일반적으로 DB의 디스크 사용량은 줄지 않아요. "삭제됨" 표시만 하고 그 공간은 나중에 재사용하기 때문이에요.

추가·변경·삭제가 반복되면 데이터가 흩어지고 빈 공간이 생기는 단편화(fragmentation)가 생겨요. 디스크 I/O가 늘어 성능이 떨어지고, 실제 데이터보다 더 많은 공간을 써요. 최적화 작업으로 데이터를 다시 정리하면 단편화와 디스크 사용량이 줄어요.

optimize table loginHistory;    -- MySQL. 큰 테이블은 오래 걸리니 한가한 시간에

3-6DB 장비 확장하기

개선 방법을 아직 못 찾았거나 시간이 필요하면, 일단 수직 확장으로 서비스를 살려 두고 개선할 시간을 벌어요. 클라우드라면 CPU·메모리 증설을 짧은 시간에 할 수 있고 효과도 눈에 띄어요. 비용은 늘지만 서비스를 못 하는 것보다 나아요.

저자의 신입 시절 경험: 평소 3~5초 걸리던 오라클 쿼리가 DB 장비 교체 후 0.5초 미만으로 줄었어요. 이른바 "장비발".

수평 확장도 가능해요. 조회 비중이 높은 서비스라면 주 DB-복제 DB(Primary-Replica) 구조가 효과적이에요.

서버
추가·수정·삭제→
주 DB (Primary)쓰기 담당
조회→
복제 DB (Replica)읽기 전용
주 DB의 변경이 복제 DB로 전파됨↓
그림 4. 변경 쿼리는 주 DB로, 조회 쿼리는 복제 DB로. 조회가 늘면 복제 DB를 추가한다
알아두기
  • DB 서버는 보통 API 서버보다 몇 배 좋은(비싼) 장비예요. 일시적인 조회 급증 때문에 늘리면 고정비가 계속 부담되니 비용 대비 이점이 확실할 때 확장해요.
  • DBA가 없는 회사라면? 복제 DB 구성은 서버 개발자에게 부담스러운 작업이에요. DB 전문 회사와 컨설팅 계약을 맺어 정기 점검·장애 대응·운영 지원을 받는 것도 방법이에요.

3-7별도 캐시 서버 구성하기

트래픽이 급증하면 여러 개선책을 써도 DB만으로는 한계가 오고, 비용 때문에 DB를 더 키우지 못할 수도 있어요. 이럴 때 캐시 서버(2장 4절)를 고려해요.

  • 대규모 트래픽 서비스 대부분이 캐시 서버를 기본으로 써요.
  • 대규모가 아니어도 캐시를 잘 쓰면 DB 확장보다 적은 비용으로 더 많은 트래픽을 처리할 수 있고, 레디스 구성은 DB 확장보다 부담도 적어요.
  • 코드 수정이 필요하지만 얻는 처리량이 크다면 합리적인 선택이에요.

4알아두면 좋을 주의 사항 6가지

4-1쿼리 타임아웃

느린 쿼리는 일정 시간이 지나면 끊어 버려야 재시도가 쌓여 서버가 죽는 것을 막을 수 있다.

응답 시간이 길어지면 처리량만 떨어지는 게 아니에요. 쿼리가 15초 걸리면 사용자는 몇 초 만에 "느리다"고 느끼고 다시 시도해요. 앞 요청이 아직 처리 중인데 새 요청이 들어오니 동시 요청 수가 빠르게 불어나고 서버 부하가 폭증해요.

타임아웃 없음

15초짜리 쿼리 실행 중 → 사용자 새로 고침 → 15초짜리 쿼리가 하나 더 → 또 새로 고침 → … 끝나지 않은 쿼리가 계속 쌓임

타임아웃 5초

5초가 넘으면 에러로 종료 → 사용자는 에러 화면을 보지만, 서버 입장에선 요청이 끝난 것이라 재시도해도 동시 요청이 폭증하지 않음

// 방법 1) 트랜잭션 단위 — 이 메서드의 DB 작업은 5초를 넘기면 예외 발생
@Transactional(timeout = 5)
public Article getArticle(long id) { ... }

// 방법 2) JdbcTemplate 전체에 기본값 지정 (application.yml)
//   spring.jdbc.template.query-timeout: 5s

// 방법 3) 특정 쿼리 하나에만 (MySQL 힌트, 단위 ms, select만 가능)
//   select /*+ MAX_EXECUTION_TIME(5000) */ * from article where ...
기능 특성에 따라 다르게

블로그 글 조회는 몇 초 이내로 짧게. 하지만 결제는 더 길게 잡아요. 결제 처리 도중 타임아웃이 나면 "돈은 나갔는데 주문은 실패" 같은 상황이 생겨서 후속 처리와 데이터 정합성 맞추기가 복잡해져요.

4-2상태 변경 기능은 복제 DB에서 조회하지 않기

"조회는 복제 DB"가 원칙이지만, 데이터를 바꾸는 기능 안에서의 조회는 주 DB에서 한다.

'변경은 주 DB, 조회는 복제 DB'를 잘못 이해해 모든 select를 복제 DB로 보내면 두 가지 문제가 생겨요.

① 복제 지연

주 DB의 변경은 네트워크로 복제 DB에 전달 → 복제 DB가 반영 두 단계를 거쳐요. 짧지만 시간이 걸리고, 그동안 두 DB의 값이 달라요.

순서일어나는 일주 DB복제 DB
1회원 가입 API 호출 → 주 DB에 회원 insert회원 있음아직 없음
2바로 이어서 복제 DB에서 그 회원을 select회원 있음아직 없음 → 조회 실패!
3(잠시 뒤) 복제 완료회원 있음회원 있음
그림 5. 변경 직후 복제 DB에서 읽으면 아직 반영 전일 수 있다
비유로 이해하기

본점 장부에 방금 적은 내용이 지점 장부에 옮겨 적히기까지는 시간이 걸려요. 본점에서 방금 가입한 손님이 바로 지점에 가서 "제 회원 정보 확인해 주세요" 하면 "그런 분 없는데요"라는 답을 들어요.

② 트랜잭션 문제

복제는 주 DB 트랜잭션이 커밋된 시점에 이뤄져요. 주 DB 트랜잭션 안에서 데이터를 바꾸고(아직 커밋 전), 그 데이터를 복제 DB에서 조회하면 변경 전 값이 나와서 문제가 생겨요.

원칙

회원 가입·변경·등록·삭제처럼 insert / update / delete를 하는 기능에서 변경 대상 데이터를 조회해야 한다면, 그 조회도 주 DB에서 해요. 복제 DB는 목록 보기·상세 보기 같은 순수 조회 기능에 써요.

4-3배치 쿼리 실행 시간 증가

큰 집계는 한 번에 하지 말고 작게 나눠서. 그리고 실행 시간을 계속 지켜보자.
용어 풀이 · 배치(batch)

사용자 요청과 무관하게 정해진 시간에 데이터를 일괄 처리하는 작업. 예) 매일 새벽 일별 회원 통계 집계, 월말 사용량 기반 요금 계산. group by + count/sum 쿼리를 자주 써요.

데이터가 늘면 배치 쿼리는 30초 → 몇 분 → 몇십 분으로 늘어요. 집계 쿼리는 메모리를 많이 써서 어느 한계점을 넘으면 몇 시간이 지나도 안 끝날 수 있어요.

  • 예방: 배치 쿼리의 실행 시간을 계속 기록·추적해서 급증을 일찍 알아차려요.
  • 가장 빠른 해결은 DB 사양 업그레이드지만 항상 가능하진 않아요. 대안은 두 가지:
    • 커버링 인덱스 활용: 집계 대상 칼럼이 인덱스에 있으면 인덱스만 스캔 → 빠르고 DB 메모리도 덜 써요.
    • 데이터를 일정 크기로 나눠 처리

✗ 한 달 치를 한 번에

select ... 각종 집계
from accessLog al
where al.accessDatetime
        >= '2024-08-01 00:00:00'
  and al.accessDatetime
        <  '2024-09-01 00:00:00'
group by ...

한계점을 넘으면 끝나지 않을 수 있어요.

✓ 하루 단위로 나눠서 31번

select ... 각종 집계
from accessLog al
where al.accessDatetime
        >= '2024-08-01 00:00:00'
  and al.accessDatetime
        <  '2024-08-02 00:00:00'
group by ...

1일~말일을 차례로 실행한 뒤 합쳐요. (필요하면 1시간·10분 단위로)

LocalDate day = LocalDate.of(2024, 8, 1);
LocalDate end = LocalDate.of(2024, 9, 1);

while (day.isBefore(end)) {
    // [day 00:00, 다음 날 00:00) 구간만 집계 → 한 번에 읽는 양이 1/31로 줄어든다
    DailyStat stat = statDao.aggregate(day.atStartOfDay(), day.plusDays(1).atStartOfDay());
    statDao.save(day, stat);       // 하루치 결과 저장
    day = day.plusDays(1);
}

나눠 처리하면 짧은 간격으로 조금씩 집계할 수도 있어요. 예) 새벽 일괄 처리 대신 10분 간격 증분 집계:

  1. 통계 테이블에 반영된 마지막 시각을 구한다
  2. [마지막 시각, 마지막 시각 + 10분) 구간의 accessLog만 집계한다
  3. 그 결과를 통계 테이블에 더한다
실제 사례 · "오늘 매출 집계 데이터가 없어요!"

I사의 매출 집계 시스템. 회계 부서가 오늘 매출 데이터가 없다고 연락했는데 담당자는 해외여행 중. 로그를 보니 한 쿼리가 3시간 넘게 실행 중이었고, DB 확장은 불가능했어요.

쿼리는 group by·집계 함수·서브 쿼리가 복잡하게 얽혀 있었고, insert … select로 조회와 저장을 한 번에 해서 테이블 잠금 시간까지 길었어요.

조치: ① insert…select를 select와 insert로 분리 → select만 먼저 실행해 정상 완료 확인 ② 결과를 한 트랜잭션이 아니라 일정 개수씩 나눠 반영 → 3시간 넘던 작업이 약 30분으로 단축.

4-4타입이 다른 칼럼 조인 주의

숫자 칼럼과 문자 칼럼을 비교하면 DB가 행마다 타입을 바꾸느라 인덱스를 제대로 못 쓴다.

user 테이블의 userId는 integer, 푸시 발송 내역 push 테이블의 receiverId는 varchar예요(수신 타입마다 식별자 형식이 달라서 문자열로 정의). receiverId에는 인덱스도 걸려 있어요.

select u.userId, u.name, p.*
from user u, push p
where u.userId = 145
  and u.userId = p.receiverId        -- integer = varchar 비교!
  and p.receiverType = 'MEMBER'
order by p.id desc limit 100;

receiverId 인덱스를 쓸 것 같지만, 타입이 달라서 DB가 비교할 때마다 각 행의 receiverId를 숫자로 변환해요. 변환한 값은 인덱스에 없으니 인덱스를 온전히 활용하지 못하고, 데이터가 많으면 오래 걸려요.

가장 단순한 형태로 보면
-- receiverId는 varchar 칼럼 + 인덱스 있음
select * from push where receiverId = 145;     -- ✗ 숫자와 비교 → 행마다 변환, 인덱스 못 씀
select * from push where receiverId = '145';   -- ✓ 문자열끼리 비교 → 인덱스 사용

따옴표 하나 차이로 explain의 type이 ALL과 ref로 갈려요. 꼭 직접 확인해 보세요.

해결: 비교하는 두 값의 타입을 맞춰요. 조인에서는 인덱스가 없는 쪽(여기서는 u.userId)을 문자열로 바꿔요. (MySQL 예)

  and cast(u.userId as char character set utf8mb4)
        collate 'utf8mb4_unicode_ci' = p.receiverId
알아두기

문자열끼리 비교할 때도 캐릭터셋(문자 집합)이 같은지 확인해요. 캐릭터셋이 다르면 그 자체로 변환이 일어날 수 있어요.

4-5테이블 변경은 신중하게

데이터가 많은 테이블의 alter table 한 줄이 서비스를 몇 시간 멈출 수 있다.

데이터가 많은 테이블에 칼럼을 추가하거나 열거 타입 칼럼을 바꿀 때는 정말 주의해야 해요.

  • 이유: MySQL은 테이블을 바꿀 때 새 테이블을 만들고 → 원본 데이터를 복사한 뒤 → 교체하는 방식을 쓰기도 해요. 복사하는 동안에는 insert/update/delete가 막혀서 그 시간만큼 서비스가 멈춰요.
  • 변경 중에도 쓰기를 허용하는 기능(온라인 DDL)이 있지만 항상 가능하진 않아요 → 데이터가 많으면 점검 시간을 잡고 변경하는 게 가장 안전해요.
  • DBA가 있으면 판단해 주지만, 없다면 스스로 판단해야 하니 더 신중해야 해요.
alter table member
  add column nickname varchar(30),
  algorithm = inplace, lock = none;
-- 온라인으로 처리할 수 없는 변경이면 실행되지 않고 에러가 난다
-- → "모르고 실행했다가 테이블이 잠기는" 사고를 막아 준다
실제 사례 · 변경 쿼리 한 줄로 8시간 중단

수천만 건 테이블의 열거 타입 칼럼을 변경하면서 온라인 DDL을 쓰지 않아 데이터 복사가 시작됐어요. 수십 분이 지나도 끝나지 않았고, 여러 기능이 쓰는 테이블이라 서비스를 점검 모드로 전환.

몇 시간 뒤 주 DB 변경이 끝났지만 복제 DB는 아직 변경 중이라 추가 시간이 필요했어요. 결국 8시간 가까이 서비스가 멈췄고, 데이터 보정·고객 보상 같은 후처리가 며칠간 이어졌어요.

운영 DB에 alter를 치기 전 체크
  • 이 테이블에 데이터가 몇 건인가? (select count(*) 또는 테이블 통계)
  • 운영과 비슷한 크기의 테스트 DB에서 얼마나 걸리는지 먼저 재 봤는가?
  • 혼자 판단하지 말고 선배·DBA에게 리뷰를 요청했는가?

4-6DB 최대 연결 개수

서버 대수 × 풀 크기가 DB의 최대 연결 수를 넘으면, 새 서버는 DB에 연결조차 못 한다.

상황: API 서버 3대, 트래픽 증가로 1대를 추가. DB CPU는 20%로 여유. 그런데 새 서버가 DB 커넥션 생성에 실패해요. 왜일까요?

DB 최대 연결 100 · 서버당 풀 30 × 4대 = 120 필요 → 20개 연결 실패
show variables like 'max_connections';    -- DB가 허용하는 최대 연결 수
show status like 'Threads_connected';     -- 지금 연결된 수

이 경우 DB의 최대 연결 개수를 늘리면 해결돼요. 단, DB CPU 사용률이 70% 이상이면 늘리면 안 돼요. 연결이 많을수록 DB 부하가 커져 성능이 떨어지기 때문이에요. 그럴 땐 먼저 캐시 서버 구성이나 쿼리 튜닝으로 DB 부하를 낮춘 뒤 필요할 때 늘려요.

5실패와 트랜잭션 고려하기

여러 데이터를 함께 바꿀 때는 "전부 성공하거나 전부 취소"되도록 트랜잭션으로 묶는다.
비유로 이해하기 · 계좌 이체

A 계좌에서 1만 원을 빼고 B 계좌에 1만 원을 넣어요. 빼기만 성공하고 넣기가 실패하면 1만 원이 사라져요. 그래서 두 작업을 하나로 묶어서, 중간에 실패하면 빼기까지 없던 일로 되돌려요(롤백). 둘 다 성공해야만 확정(커밋)해요. 이 묶음이 트랜잭션이에요.

초보가 자주 놓치는 것이 트랜잭션이에요. 코드는 늘 정상 동작하지 않으니 "중간에 실패하면 어떻게 되지?"를 반드시 고민해야 해요. 흔한 실수는 트랜잭션 없이 여러 데이터를 수정하는 것이에요.

순서실행결과
1DB 연결성공
2select * from contract where … (계약이 이미 있는지 확인)없음 → 진행
3insert into contract values (…) (계약 추가)성공 — 바로 저장됨
4update userStatus set … (사용자 상태 변경)✗ 실패
그림 6. 트랜잭션 없이 실행하다 4에서 실패하면 contract에는 데이터가 있고 userStatus는 그대로 — 둘이 어긋난다

이렇게 되면 사용자는 상태가 안 바뀌었으니 다시 계약을 시도해요. 하지만 2번에서 "이미 계약이 있음"으로 나와 더 이상 진행할 수 없어요. 가입도 안 되고 재시도도 안 되는 상태에 갇히는 거예요. 트랜잭션으로 묶었다면 4번이 실패할 때 3번도 함께 취소돼서 생기지 않았을 문제예요.

✗ 트랜잭션 없음

public void contract(ContractReq req) {
    contractDao.insert(req);       // 저장됨
    userStatusDao.update(req);     // 실패!
    // → contract만 남는다
}

✓ 트랜잭션으로 묶음

@Transactional
public void contract(ContractReq req) {
    contractDao.insert(req);
    userStatusDao.update(req);     // 실패!
    // → insert도 함께 롤백된다
}
참고 · @Transactional이 대신 해 주는 일 (SQL로 보면)
begin;                                    -- 트랜잭션 시작
insert into contract values (...);
update userStatus set status = 'ACTIVE' where userId = 100;
commit;                                   -- 둘 다 성공하면 확정
-- 중간에 실패하면 commit 대신 rollback; → 전부 없던 일로
실무 팁

DB를 변경하는 코드를 쓸 때는 트랜잭션의 시작과 끝(경계)이 제대로 설정됐는지 반드시 확인해요. 변경 쿼리가 2개 이상인 메서드에 @Transactional이 없다면 일단 의심해 보세요.

일부가 실패해도 커밋해야 하는 경우

보통은 일부가 실패하면 전체를 롤백해요. 하지만 덜 중요한 작업의 실패 때문에 중요한 작업까지 취소되면 안 되는 경우가 있어요. 예) 회원 가입 후 환영 메일 발송.

@Transactional
public void join(JoinRequest join) {
    ...
    memberDao.insert(member);     // DB에 회원 추가
    mailClient.sendMail(...);     // 메일 발송 — 실패하면 RuntimeException
}

스프링의 @Transactional은 메서드에서 런타임 예외가 밖으로 나가면 전체를 롤백해요. 메일 서버의 일시적 문제만으로 회원 insert까지 취소되는 거예요. 원하는 동작이 아니라면 메일 오류를 따로 잡아서 처리해요.

@Transactional
public void join(JoinRequest join) {
    ...
    memberDao.insert(member);
    try {
        mailClient.sendMail(...);
    } catch (Exception ex) {
        // 메일 발송 오류는 무시하되, 로그로 남겨 모니터링한다
        log.warn("환영 메일 발송 실패. memberId={}", member.getId(), ex);
    }
}
흔한 실수 · 예외를 잡고 아무것도 안 하기

catch (Exception ex) { }처럼 비워 두면 메일이 계속 실패해도 아무도 몰라요. "무시"는 "롤백시키지 않는다"는 뜻이지 "모른 척한다"는 뜻이 아니에요. 반드시 로그를 남기세요.
